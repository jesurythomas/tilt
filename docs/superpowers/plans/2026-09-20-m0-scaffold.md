### Recorded finding: `--quit` cannot be used as the boot check

Established 2026-09-20 while executing Task 1. This plan was originally written
throughout against `"$GODOT" --headless --path godot --quit`. **That command is
unusable as a verification** and every occurrence has been replaced with
`--import`. Do not reintroduce it.

| Situation | `--quit` | `--import` |
|---|---|---|
| Path does not exist | exit 1 | exit 1 |
| Directory exists, **no** `project.godot` | **exit 0** — false pass | **exit 1** |
| Valid project, no main scene | **hangs forever** | **exit 0** |

Two independent defects:

1. **It cannot fail for the right reason.** Godot only rejects a *nonexistent*
   path. Any existing directory boots the project manager and quits 0, so the
   check passes identically whether or not a project was ever loaded. It proves
   `mkdir` ran, nothing more.
2. **It hangs once a project does exist.** With no main scene defined, Godot
   4.7.2 opens a modal window titled `ALERT!` reading `Can't run project: no
   main scene defined in the project.` — **even under `--headless`** — and
   blocks indefinitely on a click that cannot arrive. Confirmed in the Windows
   process table; the runs had to be killed. Since no main scene exists until
   M2, this would hang every module from here to then.

`--import` is documented as *"Starts the editor, waits for any resources to be
imported, and then quits."* It is editor-build only, which this build is. It
was verified in both directions before being written here.

**Side effect:** `--import` creates `godot/.godot/`. Already covered by
`.gitignore`.

### Recorded finding: GUT exits 0 when a test script fails to parse

Established 2026-09-20 while executing Task 4. **GUT's exit code alone is not a
trustworthy acceptance gate.** Observed during the untyped-code proof:

- `test_scaffold.gd` failed to parse (typing violation, treated as error)
- GUT logged `[WARNING]: Ignoring script res://tests/test_scaffold.gd because it
  does not extend GutTest`, then `[ERROR]: Nothing was run.`
- **`exit=0`**

The misleading "does not extend GutTest" wording is a red herring — the script
does extend it, but the parse failed, so GUT never saw the base class.

The danger is not the single-script case above, where `Nothing was run` is at
least loud. It is the **multi-script** case from M1 onward: if one of ten test
scripts fails to parse, the other nine run, pass, print `All tests passed!` and
exit 0 — while the broken one is silently skipped. A module could be declared
green with its actual specs never executed.

No GUT flag fixes this. `-gerrors_do_not_cause_failure`, `-gfailure_error_types`
and `-gexit_on_success` all concern errors *during* test execution; this failure
happens earlier, at collection.

**Therefore, from M1 onward, never accept `exit=0` from GUT as sufficient.**
Also confirm, by reading the run summary, that the `Scripts` and `Tests` counts
are what you expected. If a module adds a spec file, the `Scripts` count must go
up. Decide the enforcement mechanism when M1 needs it — do not add tooling here
(Law 4).
