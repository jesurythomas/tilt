# Module 8 — Armory UI: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port `ArmoryUI.ts` as a touch-native `Control` scene — five tabs (weapons, ships, arena, handling, boosts), a `Theme` built from `game.css`'s tokens, and the live handling preview — reachable from the pause and game-over surfaces, with every purchase going through the `ProgressionManager` methods M7 proved; and, per the user's 2026-09-22 ruling, make purchased cosmetics visible in the run by porting the six alternate ship hulls, the enemy-skin colour arms and the arena-theme override into the render layers.

**Architecture:** `ArmoryUI.ts` becomes `src/ui/armory_ui.gd` (`class_name ArmoryUI extends Control`) with the same members in the same order (LAW 3); the TS's `innerHTML` rebuild-on-`render()` becomes a rebuild of the body's child `Control`s, so the file still reads as one `render*Tab` per tab. Its two constructor callbacks (`onStateChanged`, `onCloseModal`) become the signals `state_changed` and `closed` (UI→game, the direction spec §5.3 permits; precedent `ControlPicker.scheme_chosen`). The handling preview's canvas (`ArmoryUI.ts:943-1113`) relocates to `src/ui/handling_preview.gd`, a `_draw()` node — the same render-body relocation M3/M4/M7 made under spec §4.2/D4. The `Theme` is built in code by `src/ui/armory_theme.gd` so every token literal carries its `# PORT: web/src/styles/game.css:NN` citation (LAW 1 — a `.tres` cannot carry one); `build()` returns a real `Theme` resource, which is what spec §8 asks for. SVG icons and ship previews are the TS's own SVG strings rasterised with `Image.load_svg_from_string` (verified present in 4.7.2 on 2026-09-22 — it rendered the blackhole icon at 2× to a 60×60 image with the expected centre pixel), which lets `getShipSvgPreview` (`ProgressionManager.ts:873-939`) be ported into `progression_manager.gd` where LAW 3 puts it, reversing half of M7's Open question 1. `GameRoot` ports `openArmory`/`closeArmory`/`handleProgressionChanged`/`handleArmoryClosed` (`TiltGame.ts:2343-2385`) and pushes the equipped ship, enemy skin and arena theme into `EntityLayer`/`GridLayer` on boot and after every Armory change — the TS reads them at render time (`TiltGame.ts:2310-2312`); equipping happens nowhere else, so the two are equivalent. No sim file changes. Frame order does not change.

## The five port laws (restated — binding on every task)

> **LAW 1 — No invented numbers.** Every numeric literal carries `# PORT: web/src/tilt-to-live/<File>.ts:<line>` (or `web/src/styles/game.css:<line>` for a design token). Exempt: `0`, `1`, `-1`, `0.0`, `1.0`, array indices.
>
> **LAW 2 — No silent improvement.** If the TypeScript looks wrong, port it exactly and add `# PORT-NOTE: <what looks off> — preserved deliberately`.
>
> **LAW 3 — One file, one file.** Each TS module becomes exactly one `.gd` file, same members, same order, same names snake_cased. Sole sanctioned exception: `TiltGame.ts`, decomposed per spec §5.1. Render bodies relocate to `render/` or a `_draw()` node per spec §4.2/D4 (M3/M4/M7 precedent).
>
> **LAW 4 — Nothing new.** Not in the TypeScript or an explicit line of the spec → it does not get written.
>
> **LAW 5 — Stop, do not guess.** Genuine ambiguity → stop, record it in `HANDOFF.md`, ask.

# PORT-NOTE: toLocaleString() groups by the browser locale; en-US commas are
# fixed here — Godot has no locale-aware number formatter.
static func format_points(n: int) -> String:
	var digits: String = str(n)
	var grouped: String = ""
	var count: int = 0
	for i: int in range(digits.length() - 1, -1, -1):
		grouped = digits[i] + grouped
		count += 1
		if count % 3 == 0 and i > 0:
			grouped = "," + grouped
	return "%s %s" % [grouped, "pt" if n == 1 else "pts"]

func step() -> void:
	var current_w: float = maxf(MIN_WIDTH, size.x)
	var current_h: float = maxf(MIN_HEIGHT, size.y)
	var tuning: ProgressionManager.SteeringTuning = progression.data.tuning
	var deadzone_radius: float = maxf(DEADZONE_MIN_RADIUS, tuning.deadzone * DEADZONE_SCALE)  # :1010

	# 4. Steer ship toward cursor with real turn rate & deadzone physics
	var dx: float = mouse_pos.x - ship_x
	var dy: float = mouse_pos.y - ship_y
	var dist: float = sqrt(dx * dx + dy * dy)

	if dist > deadzone_radius:
		var dir_x: float = dx / dist
		var dir_y: float = dy / dist
		var speed_frac: float = minf(
			1.0, (dist - deadzone_radius) / maxf(SPEED_FRAC_MIN_SPAN, TOP_SPEED_RADIUS - deadzone_radius)
		)
		var max_speed: float = MAX_SPEED * tuning.sensitivity
		var target_vx: float = dir_x * max_speed * speed_frac
		var target_vy: float = dir_y * max_speed * speed_frac
		vx += (target_vx - vx) * VELOCITY_LERP
		vy += (target_vy - vy) * VELOCITY_LERP
	else:
		# Natural resting drag inside deadzone - eliminates drift
		vx *= REST_DRAG
		vy *= REST_DRAG

	ship_x += vx * STEP_DT
	ship_y += vy * STEP_DT

	# Clamping within box
	ship_x = maxf(CLAMP_MARGIN, minf(current_w - CLAMP_MARGIN, ship_x))
	ship_y = maxf(CLAMP_MARGIN, minf(current_h - CLAMP_MARGIN, ship_y))

	# Angular lerp tuned by turn rate
	var current_speed: float = sqrt(vx * vx + vy * vy)
	var target_angle: float = angle
	if current_speed > TURN_SPEED_THRESHOLD:
		target_angle = atan2(vy, vx)
	elif dist > deadzone_radius:
		target_angle = atan2(dy, dx)

	var diff: float = target_angle - angle
	while diff < -PI:
		diff += TAU
	while diff > PI:
		diff -= TAU
	angle += diff * minf(1.0, STEP_DT * ANGLE_LERP_RATE * tuning.sensitivity)

## Open questions

Each is recorded rather than resolved (LAW 5). The plan proceeds on the reading marked *recommended*; the executing session must confirm it in `HANDOFF.md` or stop.

1. **The mobile layout of the weapons tab.** `game.css:2817-2911` (≤820 CSS px) stacks the weapons sidebar above the detail (`:2854-2860`, `width: 100%`) and switches the chrome to back-button + sticky Play. A phone in landscape reports ~850 CSS px to a browser, so the web game shows the mobile chrome there. This plan gates the *chrome* on `OS.has_feature("mobile")` (Task 1, `DIVERGENCE(spec §8 M8)`) but keeps the two-column weapons *layout* on the 2340 px-wide A55, where a stacked list would waste the width. *Recommended:* two columns everywhere; the device pass (VERIFY-ME §M8 item 2) judges it. If the user wants the stacked layout, `_render_weapons_tab` swaps its `HBoxContainer` for a `VBoxContainer` and the sidebar `ScrollContainer` goes horizontal — a layout change, not a port change.

2. **The HUD's own Armory button is not ported.** `TiltGame.ts:1453-1455` binds `btn-tilt-armory-hud`, a button in the in-run HUD that opens the Armory (pausing the run). The Godot HUD carries one button (pause), positioned by the M2.5 device pass that has not yet run; a second in-run button would sit in the same provisional corner. *Recommended:* pause and game-over entries only (Task 7); the HUD button goes to M11 with the menu's entry and the rest of the HUD chrome (`TODO(M11)` in `game_root.gd`'s key handler comment). Adding it later is a scene button plus `_on_armory_pressed`, already written.

3. **`getShipSvgPreview`'s dead `'celestial'` arm.** `ProgressionManager.ts:924-930` switches on the ship id `'celestial'`, but the celestial-shaped ship's id is `revenant` (`:255-276`); the arm is unreachable and every Revenant card shows the classic arrow preview in the web game. *Recommended:* port it as written with a `PORT-NOTE` (Task 3) — LAW 2 — and let the user decide on the Ships tab whether the Revenant card should show its own hull. The fix is changing the case label to `"revenant"`, one word, plus a spec divergence tag.

4. **"Hull · N of 6 unlocked" over a seven-ship catalog.** `ArmoryUI.ts:646` hard-codes 6; `shipCatalog` has 7 entries (`ProgressionManager.ts:127-276`), so the pill can read "7 of 6". *Recommended:* port the literal (Task 3, `SHIP_COUNT_LABEL`) with a `PORT-NOTE`; the arena tab's pills use `themes.length`/`enemies.length` (`:779`, `:790`) and are correct.
